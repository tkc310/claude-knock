# 0008 タイ太陰暦の行事日は、暦法で年型を出して計算し、食い違う年だけ年型を上書きする

- 日付: 2026-10-21
- 状態: 採用（「決めたこと」1 の `supportedRange` の範囲は 0009 で変更）

## 背景

`src/core/` で、タイ太陰暦の行事 8 つの日付を出す。ワンプラは西暦 1 年に 49〜50 日ある。使うのは、Astro のビルド時の年ページ、数年分の ICS、将来の Workers である。

設計を難しくしている制約は 4 つある。

1. 公式の日付は少ない。タイ中央銀行の休日告示に載るのはブーチャー 3 行事とソンクラーンだけで、出るのは翌年分までである。ワンプラ・オークパンサー・トートカティンには、公式の日付が 1 件も無い（`docs/events/*.md`）。
2. 暦法（スリヤヤートラ系）の計算と、実際に使われる暦が食い違う年があるといわれる。
3. 正解は `tests/fixtures/official-dates.json`（17 件、2024〜2027 年、出典 URL 必須）にあり、テストはこれを正とする。
4. 行事どうしは同じ暦で結ばれている。マーカ・ブーチャーの日は、その月の満月のワンプラでもある。カオパンサーはアーサーラハ・ブーチャーの翌日で、オークパンサーはその 88 日後になる（`docs/events/README.md`）。

検討した候補は 3 つ。

- A. 暦法で閏月・閏日を計算する
- B. 公式告示の日付の表を持ち、引くだけにする
- C. A で計算し、公式告示がある年は B の日付で上書きする

## 決定

**C を変えた案（C′）を採る。暦法で決めるのは各太陰年の「年型」（平年・閏日年・閏月年）だけにする。公式の暦と食い違う年は、行事の日付ではなく年型を上書きする。公式の日付はテストの正解として使い、実行時のデータにはしない。**

### 年型と基準日 1 つで、すべての日付が決まる

タイ太陰暦で年ごとに決まることは、年型の 1 つだけである。

- 月の長さは年型で決まる。奇数月は 29 日、偶数月は 30 日。閏日年は 7 月が 30 日になり、閏月年は 8 月の後に 2 回目の 8 月（30 日）が入る。
- 年は隙間なく続く。

だから「年型の並び」と「基準日 1 つ」があれば、すべての太陰日の太陽暦の日付が決まる。基準日は、仏暦 2567 年の เดือนอ้าย ขึ้น 1 ค่ำ（1 月の白分 1 日）= 2023-12-13 とする。これは公式のアーサーラハ・ブーチャー 2024-07-20 から 220 日さかのぼった日である。

この形で試作し、次のことを確かめた（使い捨てのスクリプト、2026-10-21）。

- 暦法で出した年型（2567 = 平年、2568 = 閏日年、2569 = 閏月年、2570 = 平年）と基準日だけで、`official-dates.json` の 17 件がすべて一致した。
- 報道のカオパンサー・オークパンサー（2024〜2026 年）と、Thai PBS のワンプラの例 4 件も一致した。
- 仏暦 2560〜2610 年で、ワンプラどうしの間隔は 6・7・8 日のどれかになり、西暦 1 年あたり 49〜50 件だった。年の連続も崩れなかった。

### 上書きは年型の単位で行う

上書きの表 `YEAR_KIND_OVERRIDES` は、はじめは空にする。食い違う年が見つかったら、その年の年型を 1 行足す。

基準日から積み上げる作りなので、ある年を閏月の年に直すと、それより後の年もすべて正しくずれる。その年のワンプラ・オークパンサー・トートカティンも、一緒に正しくなる。公式告示に載らない行事まで直るのは、このためである。

上書きの表は、テストで両方向から検査する。

- 上書きの無い暦法だけで出した日付が fixtures と合わない年は、すべて上書きの表に載っていること。
- 上書きの表にある年は、すべて上書きしないと fixtures と合わないこと。効かない上書きは落とす。
- 検査が落ちたときは、3 つの年型をすべて試し、その年の fixtures をすべて満たす年型を失敗メッセージに出す。表に書き込むのは、人が出典を見てからにする。
- fixtures の日付がどの太陰年に当たるかは、`toLunar(date)` で決める。西暦年に 543 を足して対応させると、12〜1 月（1・2 月）の日付が別の年になってしまう。

### 行事の規則は `src/data/events.ts` に置く

各行事の `calendar`・`start`・`end` を、`date: DateRule` の 1 つにまとめる。規則の型とその解釈は core が持ち、値は data が持つ。

core は型引数 `E extends { date: DateRule }` を取るので、`EventId` を知らない。行事の一覧は data の 1 つだけになる。

閏月の年のずれは、規則の値として `{ common, adhikamas }` の形で書く。マーカは 3→4、ウィサーカは 6→7、アーサーラハとカオパンサーは 8→2 回目の 8 である。これは `docs/events/*.md` の書き方と 1 対 1 で対応する。

ワンプラは `{ kind: 'uposatha' }` の 1 つで表す。各月の白分 8 日・白分 15 日・黒分 8 日・月末（大の月は แรม 15、小の月は แรม 14）になる。

### ファイル分割（src/core）

| ファイル         | 持つもの                                                                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `index.ts`       | 公開 API の再エクスポートだけ                                                                                                |
| `day.ts`         | `IsoDate`（検証済みの日付のブランド型）と通算日の変換、`gregorianYear`、`addDays`、`parseIsoDate`。`Date` を使わない整数演算 |
| `suriyayatra.ts` | 太陰年から年型を出す暦法の整数演算（horakhun・kammacapon・avoman・tithi）                                                    |
| `calendar.ts`    | 年型の正本（上書きの表と暦法）、基準日、年表、`toLunar`、`formatLunarDate`                                                   |
| `rules.ts`       | `DateRule` と `Occurrence` の型、`occurrences()`、ワンプラの列挙                                                             |

呼び出しは `index → rules → calendar → suriyayatra / day` の 3 段で終わる。

年表（約 100 年 × 13 か月）は、モジュールを読み込むときに 1 回だけ作る。主な引き方は、どれも年表を 1 回引くだけで済む。

テストは、上書きなしの暦を作るために `calendar.ts` の内部を直接読み込む。`src/` の中で core の外から内部を読み込むことは、lint の `no-restricted-imports` で禁じる。

### 公開 API（src/core/index.ts）

```ts
export type IsoDate; // 実在する YYYY-MM-DD のブランド型。parseIsoDate か core の戻り値でしか作れない
export interface DateRange { from: IsoDate; to: IsoDate } // 両端を含む
export type ThaiLunarDate; // 今の項目のまま。isLeapMonth: true は 8 月のときだけ取れる共用体にする
export type DateRule =
  | { kind: 'lunar-day'; at: LunarDayRule }
  | { kind: 'lunar-span'; start: LunarDayRule; end: LunarDayRule }
  | { kind: 'uposatha' }
  | { kind: 'solar-span'; start: MonthDay; end: MonthDay };
export interface Occurrence<E> { event: E; start: IsoDate; end: IsoDate; lunar: ThaiLunarDate }

export function occurrences<E extends { date: DateRule }>(events: readonly E[], range: DateRange): Occurrence<E>[];
export function toLunar(date: IsoDate): ThaiLunarDate;
export function formatLunarDate(date: ThaiLunarDate): string; // "แรม 1 ค่ำ เดือน 8 หลัง"、"ขึ้น 8 ค่ำ เดือนอ้าย"
export function gregorianYear(year: number): DateRange;
export function addDays(date: IsoDate, days: number): IsoDate;
export function parseIsoDate(value: string): IsoDate; // 境界での検証。不正なら RangeError
export const supportedRange: DateRange; // 年表の範囲（0009 で変更）。外は RangeError
```

`occurrences` は、range の中に開始日がある行事を、開始日の順に返す。範囲を分けて呼んでも、まとめて呼んでも結果は同じで、重複も欠けも出ない。

呼び出し側は次のように使う。

```ts
// Astro の年ページ
const list = occurrences(events, gregorianYear(2026));

// ICS（2025〜2030 年）
const range = { from: gregorianYear(2025).from, to: gregorianYear(2030).to };
for (const o of occurrences(events, range)) {
  // UID は `${o.event.id}-${o.start}`。DTEND は addDays(o.end, 1)
}
```

閏月・閏日・小の月・西暦年をまたぐ 1〜2 月・上書きは、呼び出し側からは見えない。

### テストでの fixtures の使い方

1. **公開 API と fixtures**: 各行について、その西暦年の開始日の一覧が `[date]` とちょうど一致すること。ほかの日に出ていないことまで確かめる。
2. **上書きの表と fixtures**: 上の「上書きは年型の単位で行う」の両方向の検査。
3. **不変条件（fixtures に依存しない、対応範囲の全年）**:
   - 年の長さが 354・355・384 日のどれかで、年が隙間なく続く。
   - ワンプラの間隔が 6・7・8 日のどれか。
   - `docs/events/README.md` の関係表が成り立つ（カオパンサー = アーサーラハ + 1 日、オークパンサー = カオパンサー + 88 日など）。
   - `toLunar` と `Occurrence.lunar` が一致する。

## 理由

| 案                   | 正確さ                                             | 将来の年   | 保守コスト                                          | テストのしやすさ                     | ワンプラ                                             |
| -------------------- | -------------------------------------------------- | ---------- | --------------------------------------------------- | ------------------------------------ | ---------------------------------------------------- |
| A 暦法だけ           | 暦法と食い違う年を直す手段が無い                   | 出せる     | 低いが、誤りに気づけない                            | fixtures と照らせる                  | 出せる                                               |
| B 告示の表だけ       | 載る行事と年だけ正しい                             | 翌年分まで | 毎年手で写す                                        | 表を写すだけで、検査になっていない   | 公式の出典が無く、作れない                           |
| C 行事の日付を上書き | 上書きした日だけ正しく、同じ年のほかの行事とずれる | 出せる     | 告示が出るたびに上書きが増え、fixtures と二重になる | 上書きした日は、暦法の検査から外れる | 満月のワンプラが、上書きしたブーチャーの日とずれうる |
| **C′ 年型を上書き**  | 原因の年型を直すので、その年の全日付がそろう       | 出せる     | 上書きは食い違う年だけ。今は 0 行                   | fixtures が暦法全体の検査になる      | 同じ年表から出すので、満月の行事と必ずそろう         |

- B ではワンプラも 2028 年以降も出せないので、成り立たない。
- C は、同じ太陰日に 2 つの日付ができる。たとえばマーカの日を上書きしても、同じ日のワンプラは計算のまま残る。カオパンサー = アーサーラハ + 1 日のような関係も崩れる。C の「差はテストで見つける」という長所は、C′ もそのまま持っている。
- A は、C′ から上書きの表を除いたものに当たる。食い違う年が見つかったとき、暦法の式を曲げるしか直す方法が無い。

### 案の作り方（設計の統合）

2 つのモデル（opus・sonnet）が、同じ課題でそれぞれ別に設計した。もう 1 つのモデルが評価軸ごとに採点した。

2 案は、独立に同じ核に行き着いた。暦法で年の構造を出し、行事の日付ではなく年の構造を上書きする、という形である。

opus の案を土台にした。採点もこの案が上だった。

- 正本が年型の並びと基準日の 2 つだけで、年の連続が作りの上で崩れない。
- 試作で 17 件の一致を確かめてある。
- 公開の入口が `occurrences` の 1 つだけで小さい。

sonnet の案から 3 つ取り込んだ。

- 上書きの表を両方向で検査し、上書きの案を失敗メッセージに出すテスト。土台の案の検査は「その年に fixture が 1 件でもあればよい」だったので、ソンクラーンしか無い年の誤った上書きを見逃した。
- 閏月の年のずれを `{ common, adhikamas }` で書く形。土台の案の `'next-month'`（暦の並びで次の月）より、docs の書き方と対応が分かりやすい。
- 西暦の 12〜1 月の日付を、太陰年の 1・2 月として正しく対応させる注意。

採らなかったもの。

- sonnet 案の、年ごとに始まりの日を式で直接出す作り。年の始まりの日も上書きの対象になるので、閏月の年が 1 年ずれると、その年と翌年の 2 か所を上書きすることになる。基準日から積み上げれば、年型の 1 か所で済む。
- sonnet 案の、年で引く関数と期間で引く関数を両方公開すること。同じ仕事に入口が 2 つになる。

## 影響・トレードオフ

- 暦法の閾値（avoman・kammacapon など）は、まだ確かめきれていない。fixtures が 2024〜2027 年の 4 年分しかないので、暦法の分岐の一部（候補が 2 年続く年など）は公式の日付で検査されていない。代わりに、公式告示より先の年とワンプラを出せる。
- 年型で表せないずれ（暦は同じで、行事の日だけが政府の決定で動くなど）は扱えない。そういう年が来たらテストが落ちるので、そのとき設計を見直す。前もって仕組みは作らない。
- `src/data/events.ts` の `calendar`・`start`・`end` を `date` に置き換える。`tests/data.test.ts` と `src/pages/index.astro` も直すことになる。
- `IsoDate` をブランド型にするので、テストでも日付は `parseIsoDate` を通して作る。代わりに、存在しない日付が core に入らない。
- 年表をモジュールの読み込み時に作る。引き方をすべて年表 1 回で済ませるための作りで、早すぎる最適化ではない。

## 決めたこと（2026-10-21）

設計のあとで、残っていた 5 点を決めた。1 は利用者が決め、ほかは利用者から任された。2〜5 は、タイの暦（ปฏิทิน）と寺の慣習に合わせた。

1. **出す範囲は 1 年先まで。** Web と ICS が出すのは、今年と来年の行事だけにする。範囲はビルドの日から呼び出し側（`src/pages/`）が決め、`occurrences(events, { from: 今年の 1/1, to: 来年の 12/31 })` で引く。core は時計を読まない。
   - core の `supportedRange` は「暦法を確かめた範囲」で、表示の範囲とは別物である。仏暦 2567 年（基準日のある年）から、来年の分までにする。（→ 0009 で年表の全体に広げた）
   - 来年の分の公式告示は、例年その年の秋までに出る（2027 年分は 2026 年に出ている）。このため、ブーチャー 3 行事の日付は、出すときにはほぼ公式の日付で確かめられる。
2. **「暫定」の印は付けない。** タイで配られる暦は、ワンプラも含めて行事の日を印刷し、計算か公式かを分けて示さない。出す範囲を 1 年先までにしたので、ブーチャー 3 行事は告示が出た年だけになる。ワンプラ・オークパンサー・トートカティンは、もともと公式の一覧が無い。来年の告示が出て暦法と食い違えば、上書きのテストが落ちるので、そのとき年型を直す。
3. **過去の公式告示を fixtures に足すのは、今はしない。** 出す範囲が今年と来年だけなので、暦法が当たっている必要があるのもその 2 年である。その 2 年は、公式告示（2026・2027 年）で確かめてある。過去の告示で暦法の分岐をもっと確かめる作業は、バックログに残す。
4. **仏暦の年は、日付の西暦年 + 543 で表示する。** タイの暦も、タイ中央銀行の告示（「B.E. 2569 (2026)」）も、仏暦は 1 月 1 日に替わる。12 月にある太陰暦の 1 月（เดือนอ้าย）も、その 12 月の西暦年 + 543 で表示する。十二支の年（ปีนักษัตร）が 5 月で替わるという伝統的な数え方は、表示に使わない。太陰年をどう番号付けするかは core の内部のことにして、外には見せない。
5. **閏月の年に、マーカは 4 月、ウィサーカは 7 月にずらす。** これはタイの寺の慣習で、2026 年（閏月の年）の公式の日付（マーカ 03-03、ウィサーカ 05-31）もこの規則どおりである。公式の日付と合っているので、このまま使う。
6. **月の名前と閏月の呼び方は、タイの暦の言い方に合わせる。** `formatLunarDate` は、1 月を「เดือนอ้าย」、2 月を「เดือนยี่」と書き、3 月以降は「เดือน 3」のように数字で書く。閏月の年の 8 月は、1 回目を「เดือน 8 แรก」、2 回目を「เดือน 8 หลัง」と書く。
