# 定期作業と更新の仕組み

サイトを正しい状態に保つために、定期的に行う作業をまとめます。

## なぜ定期的な作業が要るのか

このサイトは静的サイト（SSG）です。行事の日付はビルドしたときに計算して HTML と `calendar.ics` に書き出すので、ビルドし直さないと変わらない部分があります。

| 表示                                    | 決まるとき                                                                      | ビルドしないとどうなるか                                             |
| --------------------------------------- | ------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| カレンダー・一覧・`calendar.ics` の期間 | ビルド時。「ビルドした年と翌年」（`src/data/display-range.ts`）                 | 年をまたぐと、新しい年の翌年の分が出ない                             |
| 冒頭の「次の行事」                      | ビルド時に候補（ワンプラ以外 8 件）を書き出し、表示時にブラウザの日付で選び直す | 候補が尽きると（おおむね半年〜1 年後）、過ぎた行事が残る             |
| 冒頭の「次のワンプラ」                  | ビルド時に候補 12 件を書き出し、表示時に選び直す                                | 約 3 か月で候補が尽き、過ぎた日付が残る                              |
| 行事カードの「次回」                    | ビルド時に表示期間内の残りの日付をすべて書き出し、表示時に選び直す              | 表示期間の終わりまでは正しい。その後は「サイトの更新後に表示」と出る |
| 「あと N 日」・カレンダーの今日の印     | 表示時（ブラウザの日付）                                                        | ビルドは要らない                                                     |

暦の計算そのもの（`src/core`）は、年表で 2123 年まで計算できます。ただし暦法で出した日付が公式の日付と合っているかは、毎年の公式告示で確かめる必要があります（ADR-0008・ADR-0009）。

## 定期作業の一覧

| 作業                       | いつ                                               | 手順                                                                                                                         |
| -------------------------- | -------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| サイトのビルドとデプロイ   | 毎日（定期ビルドができるまでは手動）。年明けは必ず | `make verify` で確かめてからデプロイする。仕組みは下の「定期ビルド」                                                         |
| 公式告示の確認（翌年分）   | 毎年秋〜年末。タイ中央銀行が翌年の休日を告示したら | `check-announcements` スキル（「告示を確認して」）。新しい日付があれば `tests/fixtures/official-dates.json` に足す PR を作る |
| 公式の出典が無い行事の確認 | 行事の前後（例: ロイクラトンは 11 月）             | `docs/improvement/backlog.md` の「暦」の項目と、`docs/events/<id>.md` の「未確認・食い違い」を見て探す                       |
| SNS 告知文の下書き（任意） | 告知したいとき（例: 毎週）                         | `event-notice` スキル（「告知文を作って」）。`docs/notices/<日付>.md` に下書きができる                                       |

公式告示と計算が食い違ったら、`tests/core/overrides.test.ts` が落ちます。`src/core/calendar.ts` の `YEAR_KIND_OVERRIDES` で、その年の年型を直します（手順は `check-announcements` スキルにあります）。

## 定期ビルド

**今はまだ無い。** デプロイ先（Cloudflare を予定。`docs/improvement/backlog.md` の「仕組み」）を用意してから作ります。それまでは手動でビルドしてデプロイします。

作るときの方針:

- 毎日 1 回ビルドしてデプロイする。日付が変わった直後（日本時間 0 時台）がよい
  - GitHub Actions の `schedule`（cron は UTC。日本時間 0:05 は `5 15 * * *`）か、デプロイ先のビルド用 URL（Cloudflare の Deploy Hook など）を定期的に呼ぶ
- ビルドする環境のタイムゾーンを `TZ=Asia/Tokyo` にそろえる。ビルドの「今日」と「今年」は、ビルドする環境の時計とタイムゾーンで決まる（`src/pages/index.astro`・`src/data/display-range.ts`）
- ビルドの前に `make check` と `make test` を通す。暦の検査（`tests/core/`）が落ちたらデプロイしない
- 毎日ビルドしても、Service Worker の版は中身が変わったときだけ変わる（ADR-0013）。中身が同じなら、利用者の端末で保存し直しは起きない

## 困ったとき

- 開発サーバー（`make dev`）で「src/content/events/<id>.md がありません」と出る: 行事の本文の項目（`src/content.config.ts`）を変えたあと、起動したままのサーバーが本文を読めていない。`pnpm exec astro dev stop` で止め、`.astro/data-store.json` を消してから起動し直す
