# 定期作業

定期作業は **年 1 回、12 月に 1 つだけ** です（ADR-0015）。

## 毎月（自動）: タイ中央銀行の API で告示を照合する

毎月 2 日に Announcements ワークフロー（`.github/workflows/announcements.yml`、ADR-0023）が、タイ中央銀行の API から今年と来年の金融機関の休日を取り、3 つのブーチャー（とカオパンサー）の日付を暦の計算と正解データ（`tests/fixtures/official-dates.json`）に照らします。手元からは `BOT_API_TOKEN=... make announcements`。

知らせることがあると、Issue が立ちます（同じ題の Issue が開いていれば、そこにコメントを足します）。

| Issue の題                             | 意味                                   | 対応                                                                     |
| -------------------------------------- | -------------------------------------- | ------------------------------------------------------------------------ |
| 正解データに無い公式の日付があります   | 新しい告示が出て、暦の計算と一致した   | 下の 12 月の 1・2 で出典を確かめて正解データに足す                       |
| 暦の計算と公式の日付が食い違っています | その年の年型（閏月・閏日）が暦法と違う | すぐ対応する。`YEAR_KIND_OVERRIDES` で年型を直し、正解データに足す       |
| 今年の告示が API から取れません        | API の不調か、トークンの期限切れ       | Actions のログを見る。トークンを作り直して `gh secret set BOT_API_TOKEN` |

Issue が立たなければ、12 月の照合の 1 を省けます（来年分が自動で確かめられているため）。

## 毎年 12 月: 翌年分の照合とビルド

12 月 1 日〜31 日のどこかで、次の 3 つを続けて行います。毎月の照合の Issue で済んでいれば、1 と 2 は要りません。

1. **公式告示の照合**: `check-announcements` スキル（「告示を確認して」）を使う。翌年分のタイ中央銀行の休日告示から日付を読み、`tests/fixtures/official-dates.json` に足す PR を作る
   - 食い違いがあれば `tests/core/overrides.test.ts` が落ちる。`src/core/calendar.ts` の `YEAR_KIND_OVERRIDES` でその年の年型を直す（手順はスキルにある）
2. **PR のマージ**: 人が中身を確かめてマージする
3. **ビルドとデプロイ**: PR をマージすると、main の CI が通った後に Deploy ワークフローが `make deploy`（build・verify の後に Cloudflare Workers へ送る）を走らせる。手元からは `make deploy`（ADR-0016）

## なぜ 12 月に 1 回で足りるのか

- **表示の期間**: サイトは「ビルドした年と翌年」の行事を出します（`src/data/display-range.ts`）
  - たとえば 2026 年 12 月にビルドすれば、2027 年 12 月 31 日まで正しく表示されます
  - 次は 2027 年 12 月にビルドすれば、2028 年の分が始まる前に出せます
- **ビルドした日に依存しない**: 「今日」の印とカレンダーの最初の月は、ブラウザの日付で決まります
  - ビルドした日に依存する「次の行事」「次回」の表示は外しました
- **告示が出揃っている**: 翌年分の中央銀行告示は、例年 8 月末ごろまでに出ます。2027 年分は 2026-08-28 に報道されています
  - 12 月なら告示が出ているので、照合を待つ必要がありません
- **照合は休日の行事だけで足りる**: 行事の日付はすべて同じ年表（年型の並び）から計算します
  - マーカ・ブーチャー、ウィサーカ・ブーチャー、アーサーラハ・ブーチャーの公式の日付が合えば、その年の年表が正しいと確かめられます
  - 休日ではない行事（アッタミー・ブーチャー、オークパンサー、ロイクラトンなど）の出典探しは、定期作業にしません。気づいたときに `docs/improvement/backlog.md` から拾います

**この形の弱み**

- 翌年の行事が見えるのは、毎年 12 月のビルドからです
- 12 月の照合を忘れても、1 月 1 日の自動のビルド（下）で表示の範囲は新しくなります。ただし翌年分は告示で確かめていない計算の日付のままです

## 定期ビルドの仕組み

デプロイは main へのマージで自動で走ります（`.github/workflows/deploy.yml`、ADR-0016）。それに加えて、**毎年 1 月 1 日 0 時 5 分（日本時間）に main を自動でビルドし直してデプロイします**（ADR-0022）。年が明けたら表示の範囲（今年と来年）が自動で 1 年進むので、その年に一度もマージが無くても、その年の行事が消えることはありません。

公開リポジトリでは、60 日リポジトリに動きが無いと定期実行が自動で止まります。`.github/workflows/keepalive.yml` が毎月 1 日に API で有効にし直します。それでも止まっていたら（Actions の画面に「disabled」と出る、GitHub から通知が来る）、`gh workflow enable deploy.yml` で有効にし直してください。

## 困ったとき

- 開発サーバー（`make dev`）で「src/content/events/<id>.md がありません」と出る場合
  - 原因: 行事の本文の項目（`src/content.config.ts`）を変えたあと、起動したままのサーバーが本文を読めていない
  - 対処: `pnpm exec astro dev stop` で止め、`.astro/data-store.json` を消してから起動し直す
